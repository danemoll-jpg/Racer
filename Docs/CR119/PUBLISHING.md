# Deliberate releases

The release destination is `danemoll-jpg/woodstock-rush-releases`. The client contains only a pinned RSA-3072 public key and public HTTPS URLs. The private signing key is under excluded local publisher storage; back it up securely and never include it in Git, runtime, ZIP, or release assets. Losing it requires a deliberate new bootstrap trust update. No GitHub credential is embedded in the client.

`Tools/Prepare-LauncherRelease.py` creates a complete initial local draft from an explicit Windows runtime and explicit designated BundleMusic root. It inventories every runtime/music file, creates the game-only ZIP, immutable per-file music assets, signed manifests, a signed catalog, and starter layout. `Tools/Prepare-ComponentUpdate.py` prepares a later game OR soundtrack release using the current signed catalog and current component manifest. It preserves the other component's pointer. Unchanged soundtrack files reuse their existing immutable URLs; withdrawn entries disappear only from the new managed manifest. Neither helper uploads.

The native client verifies RSA-PKCS1-SHA256 over the exact base64-decoded UTF-8 payload. Envelope fields: `keyId`, `payload`, `signature`. Payload schema1: catalog has independent `game` and `soundtrack` manifest URLs. Component manifests have type, platform windows-x64, minimum launcher1, monotonic build, version, notes, and files with relative path/bytes/SHA256. Game adds saveSchema and package URL/bytes/SHA256; soundtrack files add immutable URL. ZIP contents must exactly match the signed inventory. HTTPS is required in the player; loopback HTTP exists only in the separate fixture CLI.

Run the publisher with only the draft path for a dry run. `Tools/Publish-LauncherRelease.py DRAFT --publish --confirm-repository danemoll-jpg/woodstock-rush-releases` is an explicit public operation requiring authorization. It verifies the staged inventory, checks the publisher's own configured gh access, refuses an existing tag, creates a draft, uploads all immutable assets with catalog last, verifies remote sizes/digests, publishes/latest last, and fetches the permanent catalog. A failed draft remains unpublished for inspection; no blind overwrite/clobber. Keep prior releases because unchanged soundtrack URLs and rollback may reference them.

Permanent endpoint after publication: `https://github.com/danemoll-jpg/woodstock-rush-releases/releases/latest/download/update-catalog.json`. It is **not live yet**. Before making a new component draft, fetch the currently published signed catalog/manifest, verify them, and use them as previous inputs so an unrelated pointer cannot accidentally regress. Publication itself is not an automatic consequence of building.
